HMWK 3 · Encrypting, hiding and breaking messages

A toy elliptic-curve encryption scheme and the Caesar cipher, compared, and then attacked: statistics of the Italian language against Caesar, and a search of the small key space against the toy ECC.

The idea in 30 seconds

With the curve of HMWK 1 we can do more than make public keys: we can send a secret message to someone who has published a public key. The sender invents a fresh random number r and, using only the receiver's public key Q, computes a point S = r·Q that only the two of them can know. From S we build a long "random-looking" stream of bytes and we mix it with the message (XOR). The receiver, who knows the private key k, gets the same point with S = k·R and removes the stream again. Nobody else can compute S, unless they can find k from Q (the hard problem of HMWK 1).

Technically this is a simplified ECIES: an elliptic-curve Diffie–Hellman exchange followed by a symmetric stream cipher. It uses real secp256k1 parameters, but the private key is restricted to a small range so that we can attack it later in tab 5.

Who knows what? The role of each key

🔑 Private key k

Chosen by the receiver and never shared. It is used only to decrypt. Here it lies in 1 … 2b; a real scheme uses almost all of 1 … 2²⁵⁶.

🪪 Public key Q = k·G

Published by the receiver. Anyone can use it to encrypt a message for the receiver, but nobody can decrypt with it.

🎲 Ephemeral key r

A fresh random number chosen by the sender for each message. The sender sends R = r·G along with the ciphertext. Because r changes, the same message never encrypts twice in the same way.

🤝 Shared secret S

Never transmitted. The sender computes S = r·Q, the receiver computes S = k·R. They agree because r·(kG) = k·(rG).

🌀 Keystream

Bytes obtained by hashing S with Keccak-256. Encryption is message XOR keystream; decryption is ciphertext XOR keystream, which gives the message back.

The oldest cipher

In the Caesar cipher the key is a single number k from 0 to 25. To encrypt, every letter is moved k places forward in the alphabet (after Z we go back to A); to decrypt, every letter is moved k places back. Spaces and punctuation are left as they are, and accents are removed. Julius Caesar reportedly used k = 3.

Outer ring: plain letters. Inner ring: the letters they become.

Statistical properties, measured live

We encrypt the same long Italian text with both schemes and look at the symbols. The index of coincidence (IC) is the probability that two randomly chosen symbols are equal: about 0.074 for Italian letters, but only 1/26 ≈ 0.038 for uniformly random letters (and 1/256 ≈ 0.0039 for random bytes). Entropy measures the average information per symbol; the more uniform the symbols, the larger it is.

The attack in one paragraph

Italian letters are far from uniform: E, A, I and O are very common, Q and Z are rare. A Caesar cipher only relabels the letters, so the ciphertext shows the same pattern, just shifted. To find the key we try all 26 shifts and give each candidate plaintext a score that says how "Italian" it looks; the best-scoring shift is our guess. We compare four ways to score a candidate, each learned from a corpus of Italian text.

3 · How well does it work? (Monte Carlo experiment)

We take many random pieces of Italian text of a given length from the test text (never seen during training), encrypt each with a random key, attack it, and count how often the right key is found. If several shifts tie for the best score, the credit is shared between them.

What we learn

✅ Effectiveness

With a few dozen letters the key is found essentially every time, by any of the statistical methods. A key space of 26 is so small that even a crude score is enough.

📏 Length matters

Very short ciphertexts are ambiguous: several shifts can produce plausible text. Letter counts (χ²) need more letters than n-grams, because n-grams use the order of letters too, which carries much more information.

📚 Words need word boundaries

The dictionary method is easy to understand (it is what a human does), but it is the weakest on short texts and useless if spaces are removed, since it needs complete words.

⚠️ Limitations

The model must match the text: a different language, a very technical text, abbreviations, or a text written without a common letter (a lipogram) lower the success. A very small or unrepresentative corpus has the same effect (see the table above).

Comparison of approaches. Exhaustive search always works for a 26-key space, but needs a way to tell the right plaintext from the others; the dictionary does that with words, χ² does it with single-letter statistics and n-grams with letter sequences. More context per score means more reliable decisions on short texts, at the price of a bigger model.

The attack in one paragraph

The attacker sees the public key Q, the point R and the ciphertext C, and knows that the private key satisfies Q = k·G with k ≤ 2b. There are only 2b candidates, so we can try them all: compute G, 2G, 3G, … until we hit Q. A cleverer method, baby-step giant-step (BSGS), needs only about 2·√(2b) operations. Once k is known, the attacker computes S = k·R and decrypts exactly like the receiver.

How baby-step giant-step works

Write the unknown key as k = i·m + j with m ≈ √(2b) and 0 ≤ j < m. Then Q − i·(mG) = j·G. Baby steps: compute and store j·G for j = 0 … m−1 (a table of m points). Giant steps: compute Q, Q − mG, Q − 2mG, … and look each one up in the table. The first match gives i and j, hence k. We trade memory (m points) for time (about 2m operations instead of m²).

3 · Why this does not work on a properly configured ECC

Time estimates use the speed measured in your browser (35 µs per group operation). A fast computer would be thousands of times quicker, but that changes nothing for the last rows.

For a 256-bit curve the best generic algorithms (Pollard's rho, BSGS) need about 2¹²⁸ operations; BSGS would also need memory for about 2¹²⁸ points. This is why the private key must be chosen uniformly in almost the whole range 1 … n−1.

5 · Weaknesses: from the small key space, and from the design of the toy scheme

🔢 Caused by the restricted key space

Exhaustive search and BSGS recover k. The same applies to the mod-17 toy curve, where the whole group has only 9 points. A badly chosen or low-entropy key (for example derived from a short password) is attacked in the same way, even on a huge curve.

🧩 No integrity check

The ciphertext is a plain XOR, so anyone can change it in a predictable way without knowing any key. Try the demonstration below. A real scheme adds a MAC or uses authenticated encryption (for example AES-GCM).

🔁 Keystream depends on one number

Everything is derived from the x-coordinate of S. If the same r is ever used twice, the two keystreams are identical, and XOR-ing the ciphertexts removes the key completely. r must be fresh and random every time.

🛡️ Missing checks and hygiene

No validation that R is a point of the curve (invalid-curve attacks), no domain separation or salt in the key derivation, the message length is visible, and on small-cofactor curves such as the mod-17 one a small subgroup leaks information. Real ECIES standards fix these points.

Demonstration: changing a message without the key

An attacker who knows (or guesses) that the message starts with a certain word can replace it with another word of the same length, using only the ciphertext. The receiver decrypts it normally and gets the forged text.
