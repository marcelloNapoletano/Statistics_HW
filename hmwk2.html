How a list of words turns into an account, and what each cryptographic tool does along the way.

From a list of words to an address

An Ethereum wallet starts from a secret sentence of 12–24 words and ends with an address like 0xf39F…2266. In between there is a small factory line: each machine does one job and passes its result to the next one.

Worked example (a public test vector, never use it for real money): the phrase test test test test test test test test test test test junk with path m/44'/60'/0'/0/0 gives the address 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266.

🔧 The six machines

encodingchecksumderivation

BIP-39 · the words

Turns random bits into 12–24 easy-to-write words, then stretches the words into a long seed.

Like turning a huge random number into a sentence you can keep on paper.

Details: 128–256 random bits + a short SHA-256 checksum, cut into 11-bit pieces (list of 2048 words). Seed = PBKDF2-HMAC-SHA512, 2048 rounds, optional passphrase → 512 bits.

derivation

BIP-32 · the key tree

Grows a whole tree of private keys from the single seed. One backup gives you unlimited accounts.

A family tree of keys: one root, many branches.

Details: master key = HMAC-SHA512("Bitcoin seed", seed); the left half is the key, the right half is the "chain code". Hardened children (′) cannot be linked back to their parent by outsiders.

derivation

BIP-44 · the street names

Fixes a standard address for each branch of the tree, so every wallet finds the same accounts.

Like street names that all maps agree on.

Details: m / 44′ / 60′ / account′ / 0 / index. The number 44 is the standard, 60 is Ethereum.

public-key

secp256k1 · the key pair

Turns the private key k into a public key Q = k·G on an elliptic curve (HMWK 1 in miniature). Easy forwards, practically impossible backwards.

Anyone can check your signature, but only you can produce it.

Details: curve y² = x³ + 7 over a 256-bit prime field, group of about 2²⁵⁶ points.

hash

Keccak-256 · the fingerprint

Squeezes the 64-byte public key into a 32-byte fingerprint. The last 20 bytes become the address.

A blender: the smoothie tells you nothing about the fruit.

Details: sponge construction. Ethereum uses the original Keccak, which is not identical to NIST's SHA3-256.

checksumencoding

EIP-55 · the spell-check

Hides an error-detecting code in the capital letters of the address.

A typo changes the pattern of capitals, and the wallet notices.

Details: hash the lowercase address with Keccak-256; capitalise each letter whose matching hash digit is 8 or more.

🧩 Words that are easy to confuse

🎲 Key generation

Creating fresh, unpredictable randomness. In the pipeline this happens only once, at the very beginning (BIP-39 entropy).

🌳 Key derivation

Computing many keys from one secret by fixed rules: same input, same keys. BIP-39 (seed), BIP-32 and BIP-44 do this.

🗝️ Public-key cryptography

A pair of keys linked by a one-way relation; it makes digital signatures possible. Here: secp256k1.

🧮 Hashing

A fixed-size fingerprint of any data, with no key and no structure. Here: Keccak-256 (and SHA-2 inside BIP-39 and BIP-32).

✅ Checksum

Extra redundancy that catches accidental typos. It is not secret and does not stop an attacker. Here: the last BIP-39 bits and EIP-55.

🔤 Encoding

Changing how something is written without losing anything and without hiding it: words ↔ bits, bytes ↔ hexadecimal, the "0x" prefix.

🤔 Why not use one single algorithm?

Because each step needs a different kind of tool, and no known function can do all of these jobs together:

Remember & organise

BIP-39/32/44 are for human backups and for creating many accounts from one secret. They need slow, salted key stretching and a pseudorandom function, not signatures.

Prove ownership

secp256k1 lets the network check a signature without learning the secret. This needs a one-way function with algebraic structure. A hash cannot do it.

Shorten & scramble

Keccak-256 compresses the public key into a short identifier and removes all structure. A curve operation would be the wrong tool.

Catch typos

A raw address has no redundancy: one wrong digit gives another valid address and the money is lost. EIP-55 adds about 15 bits of protection without changing the format.

Splitting the work also means each part can be studied, tested and replaced on its own.

🧑‍🔬 Try it in a real wallet

Install MetaMask, Rabby or Rainbow, create a new test wallet (never use one with real money) and look for: the 12-word recovery phrase (BIP-39), the extra accounts you can add ("Account 2", "Account 3"…: these are the last number of the path in BIP-44), and the capital letters in the address (EIP-55). Importing the same phrase in another wallet gives the same addresses, which shows how deterministic derivation is.

⏳ Who came first?

Public-key cryptography (1977) came first, hash standards followed, wallet standards appeared around 2012–2014, and the standard version of Keccak and the address checksum arrived in 2015–2016.

Extra context: elliptic-curve cryptography was proposed in 1985 (Koblitz and Miller); the curve secp256k1 was defined in 2000 and chosen by Bitcoin in 2009; Keccak won the NIST SHA-3 competition in 2012; Ethereum started in 2015 using the original Keccak, before NIST finalised its own version.

🧬 SHA-2 / SHA-512 versus Keccak / SHA-3

SHA-2 / SHA-512 (2001)

Processes the message block after block with a "compression function" (additions, rotations and XOR on 64-bit words, 80 rounds). It is used inside BIP-39 and BIP-32 because its 512-bit output suits a seed.

The plain hash suffers from "length extension"; HMAC avoids that.

Keccak / SHA-3 (2012 → 2015)

A "sponge": the message is absorbed into a big 1600-bit state that is scrambled by a fixed permutation (24 rounds), then the hash is squeezed out. It was designed to be completely different from SHA-2, as a safety net.

It is not affected by length extension.

Keccak-256 is not SHA3-256

They use the same machine and the same sizes. The only difference is a small "domain separation" byte added to the message before the final padding: 0x01 in the original Keccak, 0x06 in the NIST standard. That tiny change makes every output different. For the empty message:

Keccak-256("") = c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470
SHA3-256("") = a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a

Ethereum froze the original Keccak before NIST finished its standard. So a library function called sha3 can mean either one, while Solidity's keccak256 is the original. You can try both on the next tab.
